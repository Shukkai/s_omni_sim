# KV residency across decode steps

*The model charged for re-reads a real design would not pay*

Generated by `analysis/memory/residency_run.py` — re-run it to refresh.
Model: LLaMA-3-8B on Omni-LUT, 4-bit KV, context 32,768, standard attention.

## Key findings

- **Eviction's advantage is real** — this fix was built to test whether it was an artifact of the baseline's re-reads, and the answer is no. `evict-1024` at batch 32 holds ~16x from a 0 KB buffer to a 128 MB one.
- **Residency is an energy and capacity lever, not a latency one.** At 128 MB it removes 36.8% of decode DRAM and 24.6% of decode energy, for 6.2% TPOT.
- The reason both hold: the dense K+V working set is **32 MB per layer at batch 1 and 1,024 MB at batch 32**, so no plausible buffer holds a meaningful fraction. Residency cannot rescue a cache that never fit.

## B. Does eviction's advantage survive a buffered baseline?

Both the dense baseline and the evicted run get the same buffer, so any collapse in the gap would mean eviction was really measuring residency.

**batch 1 — TPOT speedup vs dense**

| buffer | evict 4096 | evict 1024 |

**batch 32 — TPOT speedup vs dense**

| buffer | evict 4096 | evict 1024 |
|:---|---:|---:|
| 0 KB | 6.520x | 15.957x |
| 512 KB | 6.523x | 15.972x |
| 2,048 KB | 6.529x | 16.017x |
| 8,192 KB | 6.557x | 16.017x |
| 32,768 KB | 6.669x | 15.969x |
| 131,072 KB | 7.053x | 15.775x |

> **No.** The gap barely moves: at batch 1 `evict-1024` slips only 2.460x to 2.295x across a 0 KB to 128 MB sweep, and at batch 32 it does not move at all. The two are complementary rather than competing — eviction shrinks the working set to a size a buffer can hold, and residency then removes what is left. **Shrink first, then keep resident.**

## C. Where the win lands: bytes, not cycles

Context 32,768, batch 8, dense.

| buffer | DRAM saved | energy saved | TPOT gain |
|:---|---:|---:|---:|
| 512 KB | 0.1% | 0.1% | 0.0% |
| 2,048 KB | 0.6% | 0.4% | 0.1% |
| 8,192 KB | 2.3% | 1.5% | 0.4% |
| 32,768 KB | 9.2% | 6.1% | 1.5% |
| 131,072 KB | 36.8% | 24.6% | 6.2% |

> The bytes go away; the latency mostly does not. `attn_v` is compute-bound under a 4-bit KV cache, so removing its DRAM traffic moves a term that was never on the critical path — the same reason ThinK's byte saving did not become speed. **Report residency as energy and capacity, never as throughput.**
